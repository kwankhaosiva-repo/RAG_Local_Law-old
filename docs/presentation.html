บทที่ 1Chapter 1

ทำไมถึงเริ่มทำWhy we started

เรื่องมันเริ่มจากความเหลื่อมล้ำง่ายๆ — คนธรรมดาเข้าถึงคำปรึกษากฎหมายเบื้องต้นได้ยากและแพง ขณะที่กฎหมายไทยมีปริมาณมหาศาลและแก้ไขบ่อย ใครมีเงินจ้างทนายก็รู้กฎหมาย ใครไม่มีก็ได้แต่เดา It started from a simple inequality — ordinary people struggle to access even basic legal advice, and it is expensive. Meanwhile Thai law is vast and amended constantly. If you can afford a lawyer, you know the law; if you cannot, you are left guessing.

น่าจะช่วยได้… แต่ไม่ใช่ LLM ธรรมดาตัวหนึ่ง เพราะมันมีนิสัยอันตราย 3 อย่างสำหรับงานกฎหมาย: A general LLM could help… but not an ordinary one — it has three dangerous habits for legal work:

  • ตอบจากความจำเดิม — กฎหมายใหม่หรือที่แก้ไขแล้วที่อยู่นอก training data ทำให้คำตอบล้าสมัยโดยไม่รู้ตัว Answers from memory — new or amended laws outside the training data make answers silently outdated.
  • hallucinate เลขมาตรา — ที่อันตรายที่สุดคือมัน “มั่ว” แล้วดูมั่นใจมาก ยกมาตราที่ไม่มีอยู่จริงในกฎหมาย Hallucinates section numbers — worst of all, it fabricates confidently, citing sections that do not exist in the statute.
  • ค้นหาด้วยคีย์เวิร์ดแบบเดิมใช้ไม่ได้ — ภาษาไทยไม่มีการเว้นวรรคคำ และศัพท์กฎหมายเป็นทางการกว่าภาษาพูดที่คนถาม Classic keyword search falls flat — Thai has no word spacing, and legal vocabulary differs sharply from how people actually ask.
เป้าหมายของโปรเจกต์: แชทบอทที่ ค้นก่อนตอบเสมอ อ้างอิงกลับไปถึงมาตราจริงได้ และกล้าตอบว่า “ไม่พบข้อมูล” เมื่อฐานกฎหมายไม่มีคำตอบ — ความน่าเชื่อถือสำคัญกว่าความฉลาด The goal: a chatbot that always retrieves before answering, cites back to real statutes, and dares to say “not found” when the corpus has no answer — trustworthiness over cleverness.
บทที่ 2Chapter 2

เจอปัญหาอะไรบ้าง และแก้ยังไงProblems we hit — and how we fixed them

ระหว่างทางไม่ได้ราบรื่นเลย นี่คือ 7 อุปสรรคจริงที่เจอ พร้อมวิธีแก้ในโค้ดจริงของโปรเจกต์: It was anything but smooth. Here are 7 real obstacles and how they were solved in the actual codebase:

1
ปัญหาProblem

LLM มั่วเลขมาตราThe LLM fabricates section numbers

คำตอบดูผ่านหมด แต่พอไปเปิดกฎหมายจริงกลับไม่มีมาตราที่อ้างถึง — อันตรายที่สุดสำหรับงานกฎหมาย The answer looks perfect — but open the actual statute and the cited section does not exist. Fatal for legal work.

แก้:Fix: Expert Legal Prompt ห้ามอ้างมาตรานอก Context + Doc Grading ให้ LLM ให้คะแนนเอกสารก่อนตอบเสมอ ถ้าไม่เกี่ยวพอ ตอบตรงๆ ว่าไม่พบข้อมูล Expert Legal Prompt forbidding citations outside the Context + Doc Grading so the LLM scores retrieved docs before answering; if relevance is insufficient it plainly says “not found.”
2
ปัญหาProblem

ค้นคีย์เวิร์ดหาไม่เจอKeyword search finds nothing

ภาษาไทยไม่มีเว้นวรรค ศัพท์กฎหมาย (“ละเมิด”) ต่างจากภาษาพูด (“ทำผิด”) — keyword search ตรงๆ พลาดหมด Thai has no spaces; legal terms (“ละเมิด” / tort) differ from colloquial phrasing (“ทำผิด” / did wrong) — plain keyword search misses everything.

แก้:Fix: Hybrid Retrieval: Semantic (HuggingFace embeddings) + Keyword (BM25 ตัดคำไทยด้วย PyThaiNLP) รวมคะแนนด้วย Weighted RRF Hybrid retrieval: semantic (HuggingFace embeddings) + keyword (BM25 with PyThaiNLP segmentation) fused by Weighted RRF.
3
ปัญหาProblem

ค้นแต่ “คำ” ไม่เข้าใจ “เจตนา”Search matches words, not intent

Vector-only หลง keyword trap ส่วน keyword-only ไม่เข้าใจคำถาม และคำถามเทิร์น 2 อย่าง “แล้วมาตราถัดไปล่ะ” ค้นไม่ได้เลย Vector-only falls into keyword traps; keyword-only misunderstands questions; and turn-2 follow-ups like “what about the next section?” cannot be searched at all.

แก้:Fix: Weighted RRF 0.7/0.3 (vector เหนือกว่าแต่ keyword ยังมีเสียง ปรับผ่าน env) + Query Rewrite รวมประวัติแชทเป็นคำถามสมบูรณ์ก่อนค้น Weighted RRF 0.7/0.3 (vector dominant, keyword still heard, tunable via env) + query rewrite that merges chat history into a complete question before searching.
4
ปัญหาProblem

Free-tier LLM quota หมด = บริการล่มFree-tier quota runs out = outage

พึ่ง provider เจ้าเดียวพอ quota หมดหรือ service ล่ม แชทบอทตอบไม่ได้ทันที — เคยเจอจริงๆ Rely on one provider and a quota exhaustion or outage takes the bot down instantly — we actually hit this.

แก้:Fix: Multi-LLM Failover Chain (Groq → UNOROUTER → Mistral → Ollama) ส่งต่อ prompt+context ให้ตัวถัดไปทันที, error แบบ deterministic ข้ามไม่ retry, error ชั่วคราว retry 1 ครั้งด้วย backoff Multi-LLM failover chain (Groq → UNOROUTER → Mistral → Ollama) forwards prompt+context to the next provider instantly; deterministic errors skip without retry, transient ones retry once with backoff.
5
ปัญหาProblem

LINE ตัด connection ที่ 2 วินาทีLINE times out at 2 seconds

RAG + LLM ใช้เวลาหลายวินาที แต่ LINE webhook ให้เวลาแค่ 2 วินาที — ตอบช้าคือ webhook ถูกตีกลับ RAG + LLM takes seconds, but a LINE webhook only gets 2 seconds — answer slowly and the webhook is rejected.

แก้:Fix: ตรวจ X-Line-Signature → ตอบ 200 ทันที แล้วประมวลผลใน background, Reply API (ฟรี) fallback เป็น Push ถ้า reply token ใกล้หมดอายุ Verify X-Line-Signature → return 200 immediately, process in the background; Reply API (free) falls back to Push when the reply token is about to expire.
6
ปัญหาProblem

Splitter ตัดหัวมาตราเพี้ยนThe splitter mangled section heads

regex ตัวเก่าอ่าน “มาตรา ๑๕๐๗” ผิดเป็น “มาตรา ๑๕” — section_id ของ chunk เพี้ยน การอ้างอิงจึงชี้ผิดมาตรา The old regex misread “มาตรา ๑๕๐๗” as “มาตรา ๑๕” — chunk section_ids skewed, so citations pointed to the wrong section.

แก้:Fix: Thai Law Section Splitter ใหม่ จับครบทุกรูปแบบ (เลขไทย, มาตราที่ 7/1, ทวิ/ตรี/จัตวา, ข้อ) + regression test ป้องกันกลับมาเป็นซ้ำ A new Thai Law Section Splitter covering every form (Thai numerals, section 7/1, ทวิ/ตรี/จัตวา, clauses) + a regression test so it can never silently return.
7
ปัญหาProblem

Cloud Run: cold start + memory limitCloud Run: cold start + memory limit

chroma_db ~5GB โหลดตอน startup ช้ามาก และ default 512Mi ทำให้ POST /chat คืน 503 “Memory limit exceeded” The ~5GB chroma_db made startup painfully slow, and the default 512Mi returned 503 “Memory limit exceeded” on POST /chat.

แก้:Fix: สลับ Dual Vector Store ด้วย env เดียว — chroma: rsync จาก GCS เป็น background หลัง bind port; pinecone: ไม่มี cold start เลย (memory 4Gi / 2Gi ตามโหมด) Dual vector store switched by one env var — chroma: rsync from GCS in the background after binding the port; pinecone: no cold start at all (4Gi / 2Gi per mode).
บทที่ 3Chapter 3

ทำไมถึงเลือกวิธีนี้ — RAG ดีกว่าทางเลือกอื่นอย่างไรWhy this approach — why RAG over the alternatives

ทางเลือกมีแค่ไม่กี่ทาง ลองผิดลองถูกมาแล้ว: There are only a few options, and we weighed each one:

Fine-tune โมเดลเองFine-tune our own model

กฎหมายแก้ทุกสัปดาห์ → fine-tune ใหม่ทุกครั้งที่มีการแก้ไข ต้นทุนสูง ต้องมี GPU และยัง hallucinate ได้อยู่ดีเมื่อไม่มีข้อมูลใน weight The law changes weekly → retrain on every amendment: expensive, GPU-bound, and it still hallucinates when the answer is not in the weights.

Chatbot ตรงๆ ไม่มี retrievalPlain LLM chatbot, no retrieval

ตอบเร็วและง่าย แต่ไม่มีทางอ้างอิงมาตราจริงได้ และไม่มีทาง “ไม่รู้” อย่างซื่อสัตย์ Fast and easy, but it can never cite a real statute, nor honestly admit when it does not know.

RAG — ค้นก่อนตอบเสมอRAG — always retrieve first

อัปเดตข้อมูลทันทีแค่ ingest ใหม่ ไม่ต้อง train, คำตอบมีที่มาตรวจสอบได้, ควบคุมต้นทุนได้ด้วย free-tier LLM Refresh data by re-ingesting — no training. Answers have a traceable source, and cost stays low on free-tier LLMs.

คุมเข้มด้วยเกรดก่อนตอบTightened with pre-answer grading

RAG ธรรมดาอาจยังดึงเอกสารผิด → จึง ให้ LLM ให้คะแนนความเกี่ยวก่อนตอบทุกครั้ง ถ้าไม่ผ่าน ตอบว่าไม่พบ + แนะนำกฎหมายที่น่าจะเกี่ยว Vanilla RAG can still retrieve the wrong docs → so the LLM grades relevance before every answer; if it fails, the bot says “not found” and points to likely-relevant laws.

หลักคิด: ฐานความรู้แยกจากตัวโมเดล — โมเดลเป็นแค่ “นักกฎหมายที่อ่านเอกสารให้” แต่เอกสารคือความจริง และเอกสารอัปเดตได้โดยไม่แตะโค้ด Principle: separate the knowledge base from the model — the model is merely “a lawyer reading the documents,” the documents are the truth, and documents can be refreshed without touching code.

ทุกตัวถูกเลือกด้วยเหตุผลที่ตรวจสอบได้ — ตารางนี้เทียบกับทางเลือกที่ “ไม่ได้ใช้”: Every choice has a traceable reason — here is how it compares with what we did not use:

4 ขั้นของ AgentThe agent’s 4 steps

  • Route Intent: แยก “คำถามกฎหมาย” ให้ค้นฐานข้อมูล vs “คุยทั่วไป” ตอบสุภาพไม่ต้องค้น Route Intent: splits “legal questions” (→ search the corpus) from “small talk” (→ polite reply, no search).
  • Rewrite Query: รวมคำถามเทิร์นก่อนๆ ให้เป็นคำถามสมบูรณ์ก่อนค้น Rewrite Query: merges earlier turns into one complete question before searching.
  • Retrieve + Grade: ค้น hybrid แล้วให้ LLM ตรวจคุณภาพเอกสารก่อนเสมอ Retrieve + Grade: hybrid search, then the LLM always vetoes weak documents.
  • Generate: ตอบแบบนักกฎหมาย ยก quote แล้ว “สรุป:” ฟันธง พร้อมมาตรา + ลิงก์ Generate: lawyer-style answer — quote first, then a firm “summary:” with section + link.

ตัวกรองความปลอดภัย 3 ชั้นThree layers of safety

  • Prompt: ห้ามอ้างมาตราที่ไม่อยู่ใน Context — ถ้าไม่พอให้บอกตรงๆ ว่าข้อมูลไม่เพียงพอ Prompt: never cite a section absent from the Context — say plainly when evidence is insufficient.
  • Grading: เอกสารที่ค้นได้ต้องผ่านคะแนนความเกี่ยวก่อนถึงเข้าถึง generation Grading: retrieved documents must pass a relevance score before reaching generation.
  • Regression tests: ชุดเทสต์ splitter กัน section_id เพี้ยนกลับมาอีก Regression tests: a splitter test suite keeps section_ids from ever skewing again.
